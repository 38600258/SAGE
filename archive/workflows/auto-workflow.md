# 文档驱动自动化开发流程 (复杂任务强制执行)

> 本项目采用**子代理隔离执行**模式。每个阶段由独立的子代理（Sub-agent）执行，
> 通过 `ACTIVE_TASK_T-XXX.md` 文件作为唯一的跨阶段上下文桥梁。
> AI 在收到复杂任务时，**必须**按以下流程推进，不得跳过或合并阶段。

---

## 流程总览

```
/1inittask → /2review(强制) → /3dev → /4codereview(强制) → /5finish → /6deploy(手动触发)
```

| 阶段 | 触发命令 | 核心职责 | 产出物 |
|------|---------|---------|--------|
| 初始化 | `/1inittask` | 需求探测、疑问澄清、新建看板编号、拆解步骤、创建分支 | `ACTIVE_TASK_T-XXX.md` 1.1~1.5 节 + feature 分支 |
| 计划评审(强制) | `/2review` | 子代理盲审计划、红队攻击、输出修正 | `ACTIVE_TASK_T-XXX.md` 的 2.1 节 |
| 编码测试 | `/3dev` | Red-Green 循环、Lint 检查、证据链 | 代码 + 测试 + `ACTIVE_TASK` 3.1 节与 3.2 证据链 |
| 代码审查(强制) | `/4codereview` | 子代理审查 diff、证据审查与分级反馈、技术债识别 | `ACTIVE_TASK_T-XXX.md` 的 4.1 节 + 5.1 遗留问题预填 |
| 收尾归档 | `/5finish` | 技术债登记、三问结算、文档同步、Git 提交、保留分支待审 | CHANGELOG + PROJECT_BOARD + feature branch |
| 生产部署 | `/6deploy` | 前置检查、合并主分支、红线隔离审查、发版拨测 | main 分支合并 + 线上生效 |

---

## 子代理执行规范

> ⚠️ **核心架构决策**：各阶段应由独立的子代理执行，以避免单一超长会话导致的记忆衰减。
> `ACTIVE_TASK_T-XXX.md` 是跨阶段传递上下文的**唯一桥梁**。

### 子代理调用规则

| 规则 | 说明 |
|------|------|
| **上下文传递** | 调用子代理时，必须将 `ACTIVE_TASK_T-XXX.md` 的文件路径作为任务描述的核心输入 |
| **只读约束** | 子代理只能编辑 `ACTIVE_TASK_T-XXX.md` 中属于自己阶段的章节，严禁篡改其他阶段的内容 |
| **结果回收** | 子代理执行完毕后，主代理必须读取 `ACTIVE_TASK_T-XXX.md` 确认产出是否完整 |
| **失败处理** | 子代理执行失败时，主代理必须读取其产出和错误信息，决定回滚还是重试 |

### 子代理调用模板

```
任务：执行 cj-claw 项目的 [阶段名称]
任务文件：dev/docs/project/ACTIVE_TASK_T-XXX.md
工作流文件：.agents/workflows/[对应阶段].md

请严格按照工作流文件中的步骤执行。
执行完毕后，在 ACTIVE_TASK_T-XXX.md 的对应章节填写产出。
```

## 分支管理规范

所有开发任务**必须**在独立分支上进行，禁止在 `dev` 上直接编码。

### 分支命名

| 任务类型 | 格式 | 示例 |
|---------|------|------|
| 功能开发 | `feature/T-XXX-简要描述` | `feature/T-701-unified-logging` |
| Bug 修复 | `fix/T-XXX-简要描述` | `fix/T-508-session-lock` |
| 重构 | `refactor/T-XXX-简要描述` | `refactor/T-608-sync-service` |

### 分支生命周期

```
  dev─────────────────────────────────────── dev
   │                                          ▲
   └── feature/T-XXX ── commit ── commit ─── (保留分支)
       (初始化时创建)    (编码阶段)          (等待人审)
```

1. **创建时机**：阶段一（`/1inittask`）完成任务文档后，立即基于 `dev` 创建并切换到功能分支。
2. **开发阶段**：所有编码、测试提交都发生在功能分支上。
3. **合并时机**：阶段五（`/5finish`）完成后提交代码，由**人类**进行代码审查并手动合并回 `dev`。

## 阶段约束（详细版）

### 🛑 阶段一：初始化 (`/1inittask`)

**前置条件**：用户给出任务编号或描述。
**产出物**：填写完毕的 `ACTIVE_TASK_T-XXX.md`（1.1~1.5 节） + 功能分支。

在修改任何代码之前，**必须**完成以下全部步骤：

0. **环境基线对齐**：检查当前所在的 Git 分支。如果当前不在 `dev` 分支，**必须立刻执行 `git checkout dev`**，确保后续派生的功能分支及文档更新不会串线。
1. **任务锁定**：从用户获取任务编号或描述。若有编号，从 `PROJECT_BOARD.md` 确认任务目标。若无编号，视为全新需求，先收集信息。
2. **上下文加载**：根据任务性质查阅核心资产：
   - 能力全景：`dev/docs/architecture/CAPABILITY_SNAPSHOT.md`（快速了解系统当前能力边界）
   - 数据层：`db/schema.sql`、`dev/docs/architecture/`
   - 业务层：`SKILL.md`、`references/` 下的规则文档
   - 历史层：`dev/docs/project/HANDOVER-GUIDE.md`、已归档的任务记录 `dev/docs/architecture/tasks/`
   - 跨任务经验：`dev/docs/project/KNOWN_PATTERNS.md`
   - 规范层：`dev/docs/guides/development-standards.md`
3. **需求探测（禁止脑补）**：
   > 🛑 在完成本步骤并获得用户批准设计方案前，严禁进入任务拆解或编写代码。
   > 即使任务看起来"很简单"也必须走完此流程。

   **3.1 苏格拉底式逐个提问**：基于项目上下文，**一次只问一个问题**理解需求的目的、约束和成功标准。优先选择题（A/B/C），开放题为辅。如上下文中发现矛盾之处，在提问中一并澄清。若需求涉及多个独立子系统，先帮用户拆解为子项目。

   **3.2 方案探索**：充分理解需求后，**必须**提出 2-3 种技术方案，附带优劣权衡和明确推荐。结合 `CAPABILITY_SNAPSHOT.md` 优先复用现有能力。

   **3.3 分段呈现设计**：选定方案后，分段向用户呈现设计（架构、组件、数据流、错误处理、测试策略），**每段等待用户确认**后再继续。

   **3.4 等待用户批准设计**：用户确认整体方案后方可继续。绝对禁止擅自假设。
4. **需求质量自检**：对需求进行 1-5 分评估（目标清晰度/约束完整度/范围界定/可测试性），总分<12分强制停止要求补充。
5. **生成任务编号**：如果在最开始没有提供任务编号，**必须**在向人类澄清需求并自检通过后，立刻在任务看板 (`PROJECT_BOARD.md`) 中生成新的任务编号并记录。**完成此步获得编号后才能进行后续操作。**
6. **任务拆解**：运用深度思维协议（解构 → 推演 → 红队攻击），将任务目标拆解为具体到文件和函数级别的原子步骤，每步有明确验收标准。
7. **文档挂载**：
   > 🛑 **铁律**：ACTIVE_TASK 文件**必须且只能**通过物理复制模板文件产生。
   > 严禁在内存中重建模板结构，严禁用 `write_to_file` 从零生成。
   > 违反此规则将导致文档格式漂移（已验证反模式：T-711 回滚记录 #1）。

   **7.1 物理复制模板（不可跳过）**：
   ```powershell
   Copy-Item "dev\templates\TASK-TEMPLATE.md" "dev\docs\project\ACTIVE_TASK_T-XXX.md"
   ```

   **7.2 在复制后的文件上原地编辑**：
   使用编辑工具（而非重写）逐节填写：元数据 + 1.1 任务背景 + 1.2 思考与决策 + 1.3 实施计划 + 1.4 范围锁定 + 1.5 非目标。
8. **创建功能分支**：基于 `dev` 创建并切换到功能分支（命名规范见上方）。
9. **知识蒸馏与汇报**：向用户输出结构化摘要：
   - **[业务约束]**：从需求中提取的逻辑要点。
   - **[技术约束]**：架构边界、接口规范、代码复用点。
   - **[数据影响]**：涉及的数据表/内存/文件变更。
   - 展示完整的原子级任务步骤。
10. **启动子代理执行计划评审**：调用子代理进入强制的计划评审阶段（`/2review`），传递以下上下文：
    - `ACTIVE_TASK_T-XXX.md` 的文件路径
    - 工作流文件 `.agents/workflows/2review.md`
    - 指示子代理重点审阅 1.1~1.5 节

**⛔ 红线**：在完成上述步骤并获得用户授权前，严禁执行任何代码修改或命令。

### 🔙 回滚规则 (阶段一)
- **触发条件**：用户否决计划、发现需求理解偏差、外部依赖变更
- **回滚动作**：标记回滚、在 1.2 节追加回滚记录、从步骤 3 重新开始。禁止删除原有计划。

---

### 🔍 阶段二：计划评审 (`/2review`，强制)

**前置条件**：阶段一已完成，`ACTIVE_TASK_T-XXX.md` 的 1.1~1.5 节已填写。
**执行方式**：**必须由子代理执行**。主代理不得自审自己的计划。
**产出物**：`ACTIVE_TASK_T-XXX.md` 的 2.1 节（评审意见 + 修正记录）。

**子代理调用指令**：
```
任务：对 cj-claw 项目的任务计划进行盲审式红队攻击审查。
任务文件：dev/docs/project/ACTIVE_TASK_T-XXX.md
工作流文件：.agents/workflows/2review.md
审查范围：1.1 任务背景、1.2 思考与决策、1.3 实施计划、1.4 范围锁定、1.5 非目标
辅助文件：dev/docs/project/PROJECT_BOARD.md、db/schema.sql（按需读取）

你是一个独立的盲审角色，不知道计划的制定过程。请从攻击者视角审查以下维度：
1. 逻辑断层：原子步骤间是否有依赖遗漏或顺序错误？
2. 影响范围：可写文件清单是否完整？是否遗漏联动修改？
3. 边界越权：计划是否越出任务边界？
4. 副作用推演：二阶、三阶后果（并发、数据迁移、跨模块回归）
5. 测试覆盖：测试用例是否覆盖核心分支和边界条件？

将评审意见填入 ACTIVE_TASK 的 2.1 节，标注 ✅/⚠️/🛑 三级。
```

**主代理回收动作**：
1. 读取 `ACTIVE_TASK_T-XXX.md` 的 2.1 节。
2. 如有 🛑 阻塞级问题，回滚至阶段一重新规划。
3. 如仅有 ⚠️ 建议，在 2.1 节记录后进入阶段三。
4. 向用户展示评审结论摘要。

### 🔙 回滚规则 (阶段二)
- **触发条件**：评审发现阻塞性设计缺陷（🛑 级别）
- **回滚动作**：标记评审打回、记录问题要求、返回阶段一的任务拆解步骤重新规划。（仅⚠️建议时可直通）

---

### 🔴🟢 阶段三：编码与测试 (`/3dev`)

**前置条件**：阶段二已完成或直通，用户已授权编码。当前应处于功能分支上。
**会话卫生**：如当前会话已执行了完整的阶段一，**强烈建议**开启新会话执行阶段三，以避免记忆衰减。
**产出物**：通过测试的代码 + `ACTIVE_TASK_T-XXX.md` 的 3.1 节与 3.2 证据链。

严格遵守 Red-Green 循环：

1. **加载计划**：读取 `ACTIVE_TASK_T-XXX.md` 的 1.3 实施计划，如有 2.1 评审修正则纳入。确认当前在功能分支上。
2. **🔴 Red Phase（证据先行）**：
   - 在 `tests/` 创建或更新测试文件。
   - 编写覆盖核心分支和边界条件的测试用例。
   - 运行测试 `uv run pytest tests/test_xxx.py -v`。
   - **必须**展示包含 `FAIL` 或 `ERROR` 的终端输出，证明验收标准已建立。
3. **🟢 Green Phase（精准实现）**：
   - > ⚠️ **防漂移自检**：每完成一个原子步骤后，快速确认当前做的事是否还在 1.3 计划范围内？如有偏离，立即停止报告。
   - 按 1.3 计划的原子步骤逐步编写/修改代码。
   - 所有关键修改附带中文注释。
   - 每完成一个原子步骤后立即运行对应测试验证。
   - 全部完成后运行完整测试 `uv run pytest tests/test_xxx.py -v`。
   - **必须**展示包含 `PASSED` 的终端输出。
4. **跨环境验证与黑盒测试**：
   - 将代码同步至 WSL 测试环境：`.\dev\scripts\deploy.ps1 -Target wsl`。
   - 在 WSL 环境中执行核心测试，验证跨平台逻辑的稳定性。
   - **黑盒测试**：如涉及向外暴露接口或代理工具（如龙虾）的改动，必须进行黑盒测试或模拟调用，验证真实执行效果。
   - **必须**在终端输出并保存 WSL 测试和黑盒测试的客观证据。
5. **静态检查**：
   - 自动修复：`uv run ruff check --fix <文件路径>`
   - 确认清洁：`uv run ruff check <文件路径>`
   - 如有无法自动修复的问题，手动修正后重新检查。
6. **更新进度**：
   - 更新 `ACTIVE_TASK_T-XXX.md` 的 3.1 任务进度追踪。
   - 填写 3.2 证据链（测试结果(含WSL)、关键日志与黑盒测试结果、Lint 结果）。
7. **启动子代理执行代码审查**：调用子代理进入强制的代码审查阶段（`/4codereview`），传递以下上下文：
   - `ACTIVE_TASK_T-XXX.md` 的文件路径
   - 工作流文件 `.agents/workflows/4codereview.md`
   - 本次变更涉及的文件列表（供子代理定向 `git diff`）

### 🔙 回滚规则 (阶段三)
- **触发条件**：发现计划有根本性缺陷（依赖/接口问题），或测试反复失败且超出当前步骤范围。
- **回滚动作**：标记失败步骤和原因，若为计划缺陷返回阶段一重新规划，若为实现问题回退到上一个通过的原子步骤。

---

### 🔍 阶段四：代码审查 (`/4codereview`，强制)

**前置条件**：阶段三已完成，测试和 Lint 均通过。
**执行方式**：**必须由子代理执行**。主代理不得自审自己的代码。
**产出物**：`ACTIVE_TASK_T-XXX.md` 的 4.1 节（代码评审意见）+ 5.1 节（遗留问题与技术债预填）。

**子代理调用指令**：
```
任务：对 cj-claw 项目的代码变更进行深度审查。
任务文件：dev/docs/project/ACTIVE_TASK_T-XXX.md
工作流文件：.agents/workflows/4codereview.md
变更文件列表：[列出本次修改的所有文件]

你是一个独立的代码审查者。请执行以下审查：
1. 读取 ACTIVE_TASK 了解任务目标和计划
2. 通过 git diff 或逐文件阅读检查所有变更
3. 阅读 3.2 证据链中的测试结果
4. 从正确性/健壮性/一致性/性能/安全性/可测试性/证据真实性/技术债与遗留风险八个维度审查
5. 将审查意见填入 4.1 节，标注 ✅/⚠️/🛑 三级
6. 将审查中发现的技术债、未解决问题、新出现的风险逐条写入 5.1 遗留问题与技术债节（含问题描述、影响范围、建议解决思路），如无则标注"无"
```

**主代理回收动作**：
1. 读取 `ACTIVE_TASK_T-XXX.md` 的 4.1 节。
2. 如有 🛑 阻塞级问题，返回阶段三修正（同一任务打回超 2 次则升级为计划缺陷回滚至阶段一）。
3. 如审查通过，进入阶段五收尾。
4. 向用户展示审查结论摘要。

### 🔙 回滚规则 (阶段四)
- **触发条件**：审查发现 🛑 阻塞级问题
- **回滚动作**：记录审查问题，标记打回，返回阶段三按意见修正并重新提交。（同一任务打回超 2 次则升级为计划缺陷回滚至阶段一）

---

### 🔗 阶段五：收尾归档 (`/5finish`)

**前置条件**：编码测试（及代码审查）已完成。
**产出物**：CHANGELOG + PROJECT_BOARD 更新 + Git commit + 合并到 dev。

1. **遗留问题与技术债登记**：读取 `ACTIVE_TASK_T-XXX.md` 的 5.1 节（如经过 `/4codereview`，强模型已预填内容）。如该节为空或标注"无"，补充梳理未解决的问题、新出现的问题或技术债。将 5.1 节中每条遗留项**逐条登记**到 `PROJECT_BOARD.md` 的"待开发"或"阻塞项"中。
2. **知识蒸馏**：填写 `ACTIVE_TASK_T-XXX.md` 的 5.2 核心决策与避坑。将跨任务复用经验按类追加到 `dev/docs/project/KNOWN_PATTERNS.md`。
3. **任务结算三问**（填写 5.3 节）：
   - 🚢 规则同步：是否涉及业务规则永久性变更？ → 更新 `references/`。
   - 📜 决策存证：是否有关键技术取舍？ → 记录 `DECISION_LOG.md`。
   - 🛡️ 标准沉淀：是否有通用代码陷阱/最佳实践？ → 更新 `development-standards.md`。
4. **文档同步与版本控制**（参照规范 7.3 节）：
   - 严格按三层机制升版并在 `CHANGELOG.md` 建新节点：**大架构**升主版本号，**新功能**升次版本号，**Bug小更新**升修订号。
   - 将所有变更详细记录到 `CHANGELOG.md`。
   - 更新 `PROJECT_BOARD.md`（任务移入"已完成"）。
   - 如本次任务新增或变更了系统能力，在 `dev/docs/architecture/CAPABILITY_SNAPSHOT.md` 中追加或更新对应条目。
   - 同步其他受影响文档（架构文档、SKILL.md、HANDOVER-GUIDE.md 等）。
