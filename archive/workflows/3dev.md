description: 编码与测试 (Implementation & Verification)
---

> **核心原则**：严格遵守 **Red-Green** 循环——先写失败测试证明验收标准已建立，再编写代码让测试通过。

### 步骤 0：会话卫生检查 (Session Hygiene)
> ⚠️ 如果当前会话已经执行了 `/1inittask` 的完整流程，
> **强烈建议**用户开启新会话再执行 `/3dev`，
> 以避免初始化阶段的大量上下文占用导致执行阶段的记忆衰减。
> `ACTIVE_TASK_T-XXX.md` 文件是跨会话传递上下文的**唯一桥梁**，无需担心信息丢失。

### 步骤 1：加载执行计划 (Load Plan)
1. 读取 `dev/docs/project/ACTIVE_TASK_T-XXX.md` 的 **1.3 实施计划**，确认原子步骤清单。
2. 如有 **2.1 评审修正记录**，确认修正内容已被纳入执行计划。
3. 将任务阶段标记更新为 `🔴 Red Phase`。

### 步骤 2：🔴 Red Phase — 编写失败测试 (Evidence-First)
1. 在 `tests/` 目录下创建或更新与任务关联的测试文件。
2. 编写覆盖核心分支和边界条件的测试用例。
3. 运行测试：`uv run pytest tests/test_xxx.py -v`
4. **必须**展示包含 `FAIL` 或 `ERROR` 的终端输出，证明验收标准已建立。

### 步骤 3：🟢 Green Phase — 实现代码 (Implementation)

> ⚠️ **防漂移自检**：每完成一个原子步骤后，快速确认——
> 当前做的事是否还在 1.3 计划范围内？如有偏离，立即停止并向用户报告。

按照 1.3 实施计划的原子步骤，逐步实现：
1. 按步骤编写/修改代码，所有关键修改附带中文注释。
2. 每完成一个原子步骤后，立即运行对应测试验证。
3. 全部实现完成后，运行完整测试：`uv run pytest tests/test_xxx.py -v`
4. **必须**展示包含 `PASSED` 的终端输出。

### 步骤 4：静态检查 (Lint)
1. 对所有修改的文件执行自动修复：`uv run ruff check --fix <文件路径>`
2. 确认无剩余问题：`uv run ruff check <文件路径>`
3. 如有无法自动修复的问题，手动修正后重新检查。

### 步骤 5：跨环境验证与黑盒测试 (Cross-Environment & Blackbox Testing)
1. 将代码同步至 WSL 测试环境：`.\dev\scripts\deploy.ps1 -Target wsl`
2. 在 WSL 环境中执行核心测试，验证跨平台逻辑的稳定性。
3. **黑盒测试**：如涉及向外暴露的接口或代理工具（如龙虾），必须进行黑盒测试或模拟调用，验证真实执行效果。
4. **必须**在终端输出并保存上述 WSL 测试和黑盒测试的客观证据。

### 步骤 6：更新任务进度 (Progress Update)
1. 更新 `ACTIVE_TASK_T-XXX.md` 的 **3.1 任务进度追踪**，标记已完成的步骤。
2. 填写 **3.2 证据链**：
    - 自动化测试结果 (含 Windows 与 WSL)
    - 关键输出日志与黑盒测试结果
    - Lint/Type Check 结果
3. 将任务阶段标记更新为 `🟢 Green Phase 完成`。
4. 提醒提示："编码与测试完成。按照规则，下一步必须通过子代理或切换模型进行代码审查（/4codereview），除非是特殊授权免审直接收尾（/5finish）。"

### 🔙 回滚规则
- **触发条件**：
  - 编码过程中发现计划有根本性缺陷（如遗漏关键依赖、接口不兼容）
  - 测试反复失败且原因超出当前步骤范围
- **回滚动作**：
  1. 在 `ACTIVE_TASK` 3.1 节标记失败步骤和原因
  2. 元数据标记 `当前阶段: 🔙 编码回滚`
  3. 根据问题性质：
     - 计划缺陷 → 返回 `/1inittask` 步骤 4
     - 实现问题 → 在当前阶段内回退到上一个通过的原子步骤
- **记录要求**：必须在 3.1 节写明 `[回滚] 步骤 N → 步骤 M，原因：xxx`
