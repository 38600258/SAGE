# 第一部分：项目治理层

> 回答：**为什么做、给谁做、花多少钱、谁负责什么。**

## 一、 核心哲学：从"工时管理"到"容量与上下文管理"

在智能体优先的研发模式中，执行主体变为智能体，**项目管理的核心对象转变为"管上下文"与"控流（Flow）"**。

```
传统敏捷：以"人天"为瓶颈 ──> 拆解工时 ──> 日报/站会监控 ──> 交付延迟
智能体敏捷：以"人类审查容量"为瓶颈 ──> 控制PR大小 ──> 自动化队列拦截 ──> 持续合并
```

### 三大精益管理定律

1. **人类审查带宽是唯一瓶颈**：项目吞吐量取决于人类 Reviewer 能审多快，而不是智能体写得多快。
2. **小步提交（Micro-PR）是防错底线**：单个 PR 的 Diff 超过 200 行时，人类发现逻辑缺陷的概率断崖式下跌。
3. **不确定性向两端收敛**：聚焦"前置需求确定性"与"后置测试确定性"，中间的编码过程采用 WIP 自适应排队。

## 二、 项目启动与章程（Project Initiation）

> **反模式警告**：没有章程就启动编码 = 没有地图就出发。智能体会高效地把你带到你不想去的地方。

### 1. 单页章程模板（A4 Charter）

每个项目/史诗级任务启动前，上下文架构师必须填写以下单页章程并获得 Sponsor 签字：

| 字段 | 说明 | 示例 |
|------|------|------|
| **项目名称** | 一句话命名 | CJ-SaaS 支付网关重构 |
| **商业论证** | 为什么要做？不做的后果？ | 当前支付失败率 3.2%，月损失 ¥12 万 |
| **成功标准** | 可度量的完成条件（≤ 3 条） | 支付失败率 < 0.5%；P99 延迟 < 800ms |
| **范围边界** | 做什么 / **不做什么** | 做：重构网关；不做：不动前端支付页 |
| **关键里程碑** | 最多 5 个时间节点 | M1: 设计评审 → M2: 联调 → M3: 灰度 |
| **预算框架** | 人力 + Agent API + 基础设施 | 2 人×4 周 + API ¥3000 |
| **Sponsor** | 最终决策人（有权叫停） | @张总 |
| **关键假设与约束** | 隐含前提 | 假设：支付宝 SDK 接口不变 |

### 2. 可行性门禁

章程提交后必须通过以下三项可行性检查，否则**禁止进入任务拆解阶段**：
- [ ] **技术可行性**：核心技术方案是否已有 PoC 或参考实现？
- [ ] **资源可行性**：人类 Reviewer 带宽是否足够支撑预估的 PR 量？
- [ ] **时间可行性**：里程碑是否与外部强依赖（如合同截止日）对齐？

## 三、 干系人与沟通管理

### 1. 干系人 RACI 矩阵

在项目启动时，上下文架构师必须定义以下 RACI 矩阵：

| 活动 | Sponsor | 上下文架构师 | 质量守门人 | 不变量定义者 | 智能体牧人 | 智能体 |
|------|---------|------------|----------|------------|----------|--------|
| 项目章程审批 | **A** | R | C | - | - | - |
| 需求确认 | **A** | R | C | I | I | - |
| 任务拆解 (WBS) | I | **A/R** | C | C | - | - |
| 代码开发 | - | I | - | - | C | **R** |
| 代码审查 | - | I | **A/R** | C | - | - |
| 发布决策 | **A** | R | R | - | - | - |
| 事件应急响应 | I | C | **A/R** | R | R | - |

> R=执行 A=批准 C=咨询 I=通知

### 2. 沟通矩阵

| 沟通事件 | 频率 | 发起方 | 参与方 | 渠道 | 产出物 |
|---------|------|--------|-------|------|--------|
| 项目状态同步 | 每周 | 上下文架构师 | 全体 | 异步文档 | `STATUS_REPORT.md` |
| 里程碑评审 | 每里程碑 | 上下文架构师 | Sponsor + 全体 | 同步会议 | 决策记录 → `DECISION_LOG.md` |
| 风险升级 | 触发式 | 任何人 | 上下文架构师 | 即时通讯 | 风险登记册更新 |
| 变更请求 (CCB) | 触发式 | 智能体/牧人 | CCB 委员会 | Linter 拦截 → 文档 | TASK 文档 1.4 节更新 |
| 事件通报 | 触发式 | On-Call | 全体 | 即时通讯 | 事件报告 |

### 3. 升级路径（15 分钟规则）

```
智能体受阻（Blocked）
  └──> 15 min 内 ──> 智能体牧人介入排障
         └──> 30 min 仍未解决 ──> 上下文架构师决策
                └──> 涉及架构/安全 ──> 质量守门人 + Sponsor 联合裁决
```

## 四、 角色与职责矩阵

### 人机协同的新型研发链

| 角色 | 智能体时代定位 | 核心管控点 | 关键产出 |
| :--- | :--- | :--- | :--- |
| **上下文架构师** | 前置输入守护者 | - 阻断模糊需求<br>- 编写结构化 PRD<br>- 维护看板与排期 | `PRD-XXX.md`<br>`PROJECT_BOARD.md` |
| **质量守门人** | 后置风险拦截者 | - 高风险设计计划盲审<br>- 架构与安全审计<br>- 合并与发布门禁 | `ADR-XXX.md`<br>PR Approve/Merge |
| **不变量定义者** | 质量自动线建设者 | - 编写核心不变量（测试、Lint 规则）<br>- 设计静态检查逻辑 | 自动化验证套件 |
| **智能体牧人** | 现场环境支撑者 | - 启动智能体并分配任务<br>- 排障环境/网络/依赖问题 | 启动命令与现场决策 |

### 宿主角色映射

SAGE 方法论中的抽象角色，在不同宿主中有对应的实现映射：

| SAGE 角色提示词 | 宿主实现 | 说明 |
| :--- | :--- | :--- |
| `orchestrator` | **Main Agent 职责** | Main Agent 是当前主会话/主工具代理；`prompts/orchestrator.md` 仅在流程分级、阶段选择或外包边界不确定时作参考 |
| `planner` | **Main Agent 主线程**，复杂任务可派生辅助草拟子代理 | 需求澄清、范围取舍、最终计划确认必须保留主线程 |
| `coder` | **执行通道配置**（CLI / subagent / Main Agent） | 默认按 `docs/guides/execution-channels.md` 选择载体 |
| `reviewer` | **执行通道配置**（CLI 首选，subagent 备选） | 注入 `prompts/reviewer.md`，物理隔离保证盲审独立性 |
| `closer` | **执行通道配置**（CLI / subagent / Main Agent） | 默认按 `docs/guides/execution-channels.md` 选择载体 |

SAGE skill 可以内置 `prompts/`、`templates/` 和核心 `docs/guides/` 作为默认发行版，降低新项目接入成本。项目一旦初始化出本地 `prompts/*.md` 等文件，本地文件就是该项目权威来源；CLI 和 subagent 仍只是执行适配器或载体，只能读取并承载当前权威版本。

> 执行通道配置详见 `docs/guides/execution-channels.md`，模型选择策略详见 `docs/guides/model-selection.md`。

### 团队容量基线

在项目规划阶段必须确认以下容量参数：

| 参数 | 计算方法 | 典型值 |
|------|---------|--------|
| **人类日审查容量** | 每人每日可审查的 PR 数 × 人数 | 5 PR/人/天 |
| **人类日审查行数** | 每人每日可审查的 Diff 总行数 × 人数 | 1000 行/人/天 |
| **智能体并发数** | 可同时运行的智能体会话数 | 取决于 API 额度 |
| **WIP 上限** | min(日审查容量, 智能体并发数) | 通常 3-5 |

## 五、 需求管理

### 1. 需求输入标准（Definition of Ready）

任何需求在进入任务拆解之前，必须满足以下"就绪定义"：

- [ ] **用户故事格式**：`作为<角色>，我需要<功能>，以便<价值>`
- [ ] **验收标准**：至少 2 条可客观验证的行为描述
- [ ] **技术约束**：明确的技术边界（如 API 兼容性、性能基线）
- [ ] **非目标清单**：明确列出**不做**的事情（防止需求漂移）
- [ ] **依赖确认**：外部依赖（第三方 API、其他团队交付物）是否已就绪

### 2. 需求追踪矩阵（RTM）

每个需求必须可追溯到：需求来源 → PRD 条目 → 任务编号 → 测试用例 → 代码变更。

```
[Stakeholder 需求] ──> [PRD-XXX 条目] ──> [TASK T-XXX] ──> [Test Case] ──> [Git Commit]
         ↑                                                                      │
         └────────────── 双向追溯，变更时同步更新 ──────────────────────────────────┘
```

## 六、 预算与资源规划

### 1. 智能体时代的成本模型

| 成本类别 | 度量单位 | 典型控制手段 |
|---------|---------|-------------|
| **Agent API 调用** | Token 数 × 单价 | 设置每任务/每日 Token 上限 |
| **人类审查工时** | 审查 PR 数 × 平均时长 | WIP 限制 + PR Size Limit |
| **基础设施** | CI/CD 运行时 + 测试环境 | 按需扩缩 + 缓存优化 |
| **返工成本** | 被打回次数 × 平均修复耗时 | 前置防御（Author Self-Review） |

### 2. 成本基线与预警

- 在项目章程中设定**成本基线**（预算天花板）。
- 当累计消耗达到基线的 **80%** 时，自动触发预警，上下文架构师必须评估剩余工作量。
- 超出基线必须走 CCB 变更流程获得 Sponsor 批准。

## 七、 任务拆解（WBS）与风险流转机制

### 1. 智能体优先 WBS 拆解原则
*   **物理体积锁定 (Micro-PR)**：单个任务的可写文件原则上**不超过 3 个源文件**，或预期 Diff **小于 200 行**。
*   **无环依赖链 (DAG)**：任务按文件修改的物理依赖关系拓扑排序。前置任务未合并，下游任务不得进入 `Ready`。
*   **前置防御 (Author Self-Review)**：智能体在交付前必须自行运行 `sage_linter` 并阅读 Diff，确保无低级错误后才提交。

### 2. L1/L2/L3 风险流转状态机

```
[Backlog] ──> [Todo] ──> [Ready] ──> [Doing] ──> [Blocked] ──> [Done]
```
*   **L1 轻量**（纯文档、单元测试补充、无副作用重构）：可跳过计划/代码盲审；合并仍由人类或人类配置的外部队列执行。
*   **L2 标准**（日常业务开发、Bug 修复）：必须经过阶段二（计划盲审）与阶段四（代码盲审），人类手动合并。
*   **L3 高危**（DB 迁移、架构变更、敏感支付）：智能体输出阶段报告后自动进入 `Blocked`，必须人类命令行放行。

跨阶段派发时，L1 及以上 TASK 文档是调度信息来源：Main Agent 在主线程执行规划；向 reviewer/coder/closer 外包阶段任务时，应传入 TASK 文档路径和对应角色提示词路径。角色必须从 TASK 文档元数据读取任务等级、当前阶段、项目根目录和功能分支；若风险等级缺失，按 L2 处理并记录默认决策。L0 不进入跨阶段派发。

当审查、编码、收尾三阶段交给 CLI 工具处理时，Main Agent 仍负责阶段流转和门禁判断。CLI 调用从 `docs/guides/execution-channels.md` 读取命令模板，必须只接收冻结 TASK 文档、对应角色提示词和必要证据，不携带主线程讨论历史。

任务等级不仅决定阶段链，也决定角色行为强度：

| 等级 | 编排策略 | 质量策略 |
|------|----------|----------|
| **L0** | 主代理直接处理，不创建 TASK、不启动子代理 | 最小相关验证，确认无范围扩张，中文提交 |
| **L1** | 主代理主导，coder/closer 可选 CLI 化 | 跳过盲审但保留测试/lint/门禁 |
| **L2** | planner 主线程，coder/closer 可 CLI 化，reviewer 独立 | 双盲审、完整证据链、收尾归档 |
| **L3** | 主代理控制流转，子代理只处理冻结输入 | 每阶段人工确认，强化回滚、授权和残余风险记录 |

### 3. Subagent 并行执行策略

在 WBS 拆解后，利用宿主子代理能力（如可用）实现任务内的角色并行：

```
Main Agent（编排器）
  ├── Research Subagent ──> 异步调研技术方案、收集参考实现
  │     └─ Workspace: inherit（只读研究，不修改代码）
  ├── Coder Channel ──> 按原子步骤编码 + Red-Green 循环
  │     └─ CLI 或 subagent，按 execution-channels 配置
  └── Reviewer Channel ──> 盲审计划或代码（物理隔离）
        └─ CLI 首选，注入 prompts/reviewer.md
```

**并行规则**：
- Research Subagent 与 Coder Channel 可并行（无文件写入冲突时）
- Reviewer Channel 必须在编码完成**之后**串行触发（盲审依赖最终产出物）
- 冲突敏感型任务（可写文件有交集）严禁分配给不同 Coder Channel 并行
- 只有在 L1 及以上 TASK 1.1~1.5 已冻结且任务等级允许时，Coder/Closer 子代理才可启动
- 启动 Coder/Closer CLI 或子代理时必须传入 TASK 文档路径和角色提示词路径；调度信息从 TASK 元数据读取，风险等级缺失按 L2
- 规划默认保留主线程；只有复杂 L2/L3 才考虑额外草拟子代理

## 八、 宏观排期与合并地狱防范

### 1. 限制在制品 (WIP Limit)
对于单个代码库，处于 `Doing` 状态的 L2/L3 任务上限为 **3 个**。超限任务必须在 `Ready` 排队。

### 2. 关键路径依赖管理 (CPM)
*   **空间隔离**：若两个任务的 `1.4 可写文件` 有交集，判定为冲突敏感型任务。
*   **串行序列化**：冲突敏感型任务严禁分配给不同智能体并行执行，强制设定先后依赖。

### 3. 开发主干集成与合并队列
*   **开发主干集成 (Dev Mainline Integration)**：默认基于项目开发基线分支（通常为 `dev`，小型项目可为 `main`）进行日常集成。Feature 分支生存周期原则上不超过 24 小时。
*   **人类合并权**：Reviewer 批准只代表质量门禁通过，不代表智能体可自动合并。合并到 `dev` / `main` / 发布分支必须由人类授权或由人类配置的外部 CI/合并队列执行。

### 4. 定时巡检实现 WIP 状态自动巡检

使用 cron 或宿主定时任务能力配置定时巡检，自动监控 WIP 状态健康度：

```bash
# 每 30 分钟巡检一次在制品状态（cron 语法；载体为宿主定时任务能力）
"*/30 * * * *" "检查 PROJECT_BOARD.md 中 Doing 状态任务数量，
  若超过 WIP 上限（3 个）则发出预警；
  若任一任务 Cycle Time 超过预期 2 倍则标记为风险项"
```

巡检覆盖范围：
- WIP 数量是否越限
- 单任务停滞时间是否异常（超过 Cycle Time 阈值的 2 倍）
- 功能分支生存周期是否超过 24 小时

## 九、 质量管理体系

> 质量管理 ≠ 代码审查。代码审查只是质量保证的一个环节。

### 1. 测试金字塔策略

| 测试层 | 覆盖目标 | 执行者 | 执行时机 | 覆盖率要求 |
|--------|---------|--------|---------|-----------|
| **单元测试** | 函数/模块级逻辑 | 智能体（coder） | 每次提交 | ≥ 80% 行覆盖 |
| **集成测试** | 模块间交互/API 契约 | 智能体（coder） | PR 提交时 | 核心链路 100% |
| **E2E 测试** | 关键用户旅程 | 不变量定义者 | 合并到 `dev` 后 | 核心场景全覆盖 |
| **性能测试** | 延迟/吞吐量基线 | 不变量定义者 | 里程碑前 | P99 达标 |
| **安全扫描** | 已知漏洞/敏感信息 | CI 自动化 (SAST/SCA) | 每次提交 | 零高危漏洞 |

### 2. 质量门禁定义（Quality Gates）

| 阶段 | 门禁名称 | 检查项 | 阻断级别 |
|------|---------|--------|---------|
| 阶段 1 出口 | **计划就绪门** | 验收标准 ≥ 2 条 + 可写白名单已锁定 | L2/L3 强制 |
| 阶段 3 出口 | **代码交付门** | 测试全过 + Lint 零错 + Diff ≤ 200 行 | 全部强制 |
| 阶段 4 出口 | **合并就绪门** | 人类审查通过 + 无遗留 TODO | L2/L3 强制 |
| 发布前 | **生产就绪门** | E2E 通过 + 性能基线达标 + 回滚方案就绪 | L3 强制 |

## 十、 人类"盲审疲劳"治理

### 1. 政策分工法（Policy-Based Review）
人类 Reviewer 明确**不审查**以下维度（完全移交自动化）：
*   ❌ 代码格式、缩进、命名拼写（Linters 保证）
*   ❌ 单元测试是否通过（CI 报告保证）
*   ❌ 基本语法错误（静态分析器拦截）
*   **✅ 人类只审查：** 二阶/三阶副作用、设计模式一致性、架构取舍（ADR）合理性

### 2. 轮值与限额防线
*   **单日配额**：每人每日审批 ≤ 5 个 PR，或总 Diff ≤ 1000 行。超限自动分流。
*   **智能体自救熔断**：同一任务连续被打回 ≥ 3 次，强制 `Blocked` 并通知人类接管。

### 3. CLI 自动化盲审：卸载人类审查负担

CLI 盲审机制（见执行通道指南）可将大量**格式化、机械性审查**从人类肩上卸载：

```powershell
# 计划盲审（阶段二）：生成派发信封后按 adapter 执行（原生 subagent 或 CLI 命令数组）
uv run python scripts/sage_dispatch.py prepare --repo-root <repo> --task-path <task> --phase plan-review --adapter <adapter> --format json

# 代码盲审（阶段四）：同上，--phase code-review 并按需附加 --diff-cmd
```

**盲审隔离保证**：独立 CLI 进程或注入式子代理**没有** Main Agent 的对话历史，天然实现物理隔离——审查者不知道计划的制定过程，只看到产出物。

**人类审查聚焦**：CLI 盲审处理五/八维度的机械性检查后，人类只需聚焦于：
- 二阶/三阶副作用的**业务判断**
- 架构取舍的**战略合理性**
- CLI 审查报告中 🛑 阻塞项的**最终裁决**

## 十一、 变更控制与 CCB 机制

当智能体修改了 `1.4 声明` 外的文件时，`sage_linter` 自动拦截：

```
[临时新增需求]
     │
     ▼
[Linter 拦截] (修改了 1.4 白名单外文件)
     │
     ▼
[智能体挂起 Blocked] ──> 发起 CCB 申请 ──> 人类评估
                                            │
                  ┌─────────────────────────┴───────────────────┐
                  ▼ (拒绝)                                       ▼ (批准)
             撤销多余修改                                1. 更新 TASK 1.1 和 1.4 节
             继续任务                                    2. 重新运行 Linter
                                                         3. 智能体继续
```

### CCB 流程
1. **停止当前执行**：智能体报告拦截原因，状态标为 `Blocked`。
2. **人类决策**：上下文架构师 + 质量守门人组成最小 CCB，评估影响。
3. **书面确认**：手动更新 TASK 文档的需求范围和白名单，重新签署变更契约。

### Hooks 自动触发 sage_linter

宿主提供写入后钩子能力（PostToolUse 或等效机制）时，可配置**每次文件写入后**自动运行范围校验：

```json
// 钩子配置示例（字段名以宿主规范为准）
{
  "trigger": "PostToolUse",
  "tools": ["<宿主文件写入工具名>"],
  "command": "python scripts/sage_linter.py --check-scope docs/project/ACTIVE_TASK_T-${TASK_ID}.md",
  "onFailure": "block"
}
```

宿主无写入后钩子时，以 Git hooks（commit-msg/pre-commit）作为兜底防护。

**物理防护效果**：智能体每次写入文件后，Hook 自动触发 `sage_linter` 的范围锁定校验（校验项 10）。若写入的文件不在 TASK 1.4 白名单中，Hook 返回失败并阻断后续操作，智能体进入 `Blocked` 状态。这将 CCB 拦截从"事后发现"提升为"实时阻断"。

## 十四、 度量与 KPI 体系

### 1. 项目健康仪表盘（四类指标）

#### A. 流量指标（精益）

| 指标 | 定义 | 健康阈值 | 数据来源 |
|------|------|---------|---------|
| **Lead Time** | 需求提出 → 生产交付 | L1: < 4h / L2: < 2d / L3: < 1w | 看板 + Git |
| **Cycle Time** | 任务开始 → 任务完成 | L1: < 1h / L2: < 8h / L3: < 3d | 看板 |
| **Throughput** | 每周完成的任务数 | 趋势上升或稳定 | 看板 |
| **WIP Age** | 在制品停留时间 | 不超过 Cycle Time 的 2 倍 | 看板 |

#### B. 质量指标（DORA + 自定义）

| 指标 | 定义 | 健康阈值 | 数据来源 |
|------|------|---------|---------|
| **部署频率** | 每周部署到生产的次数 | ≥ 3 次/周 | CI/CD |
| **变更失败率** | 导致生产回退的部署占比 | < 5% | 事件记录 |
| **MTTR** | 从事件发生到恢复的平均时间 | < 1 小时 | 事件记录 |
| **返工率** | 被打回重做的任务占比 | < 15% | 看板 |
| **测试覆盖率** | 核心模块代码行覆盖率 | ≥ 80% | CI 报告 |

#### C. 效能指标（Agent 特有）

| 指标 | 定义 | 用途 |
|------|------|------|
| **Agent 代码采纳率** | Agent 生成代码被合并的比例 | 衡量 Agent 有效性 |
| **Agent 熔断率** | 触发熔断（≥3 次打回）的任务占比 | 检测 Agent 能力边界 |
| **人类干预率** | 需要人类从 Blocked 中解救的任务占比 | 衡量自治度 |
| **Token 消耗/任务** | 单个任务的平均 API Token 消耗 | 成本控制 |

#### D. 业务指标

由 Sponsor 在项目章程中定义，与项目成功标准直接挂钩（如：支付失败率、页面加载时间）。

### 2. 指标评审节奏
*   **每周**：上下文架构师在 `STATUS_REPORT.md` 中更新流量 + 质量指标。
*   **每里程碑**：全量指标评审 + 趋势分析 + 偏差纠偏。

## 十五、 事件管理与应急响应

### 1. 事件分级

| 级别 | 影响范围 | 响应时效 | 处置方式 |
|------|---------|---------|---------|
| **P0 灾难** | 核心业务完全中断 | 立即响应 | 全员集合、回退优先、Sponsor 通报 |
| **P1 严重** | 核心功能受损、影响部分用户 | 15 分钟内 | On-Call 响应、回退或热修 |
| **P2 一般** | 非核心功能异常、有临时绕行方案 | 2 小时内 | 登记为 L2 任务排入下一迭代 |
| **P3 轻微** | UI 瑕疵、文案错误 | 下一迭代 | 登记为 L1 任务 |

### 2. 事件响应流程

```
[监控告警/用户报告]
    │
    ▼
[On-Call 确认] ──> 15 min 内判定级别
    │
    ├── P0/P1 ──> 立即回退 ──> 通报干系人 ──> 事后复盘
    │
    └── P2/P3 ──> 登记为任务 ──> 排入看板
```

### 3. 关键规则
*   **严禁智能体在生产环境在线 Debug**。P0/P1 事件必须先回退，再在隔离环境复现和修复。
*   事件解决后 **48 小时内**必须完成事后复盘（见第十六章）。

## 十六、 回顾与持续改进

### 1. 三级回顾节奏

| 级别 | 频率 | 时长 | 参与者 | 产出 |
|------|------|------|--------|------|
| **任务回顾** | 每个 L2/L3 任务完成后 | 10 min | 智能体牧人 + 架构师 | TASK 文档 5.2 节 |
| **迭代回顾** | 每 2 周 | 30 min | 全体人类角色 | `RETRO_YYYY-MM-DD.md` |
| **里程碑回顾** | 每里程碑 | 60 min | 全体 + Sponsor | 改进 Action 清单 |

### 2. 迭代回顾模板（WWW/TALA）

```markdown
## 迭代回顾 YYYY-MM-DD

### 做得好的 (Went Well)
- ...

### 需改进的 (To Adjust)
- ...

### 学到的 (Learned)
- ...

### 行动项 (Actions)
- [ ] 具体改进措施 → 责任人 → 截止日期
```

### 3. 事后复盘（Blameless Post-Mortem）

所有 P0/P1 事件和 Agent 熔断事件必须执行无指责事后复盘：
1. **时间线重建**：从第一个信号到完全恢复的完整事件链。
2. **5 Whys 根因分析**：至少问五次"为什么"，追溯到系统性原因。
3. **改进项跟踪**：每个改进项必须转化为具体任务（T-XXX），排入看板，不允许停留在"下次注意"。

## 十八、 Agent 治理与可观测性

### 1. Agent 权限最小化原则

| 权限维度 | L1 任务 | L2 任务 | L3 任务 |
|---------|---------|---------|---------|
| **文件写入** | 仅 TASK 声明的可写白名单 | 同左 | 同左 |
| **命令执行** | 构建 + 测试命令 | 构建 + 测试 + 迁移（dry-run） | 仅构建 + 测试 |
| **网络访问** | 包管理器 | 包管理器 + 文档站 | 包管理器（受限） |
| **自主合并** | ✅ CI 通过后自动合并 | ❌ 需人类批准 | ❌ 需人类批准 |

#### 宿主权限映射：授权卡片矩阵

宿主提供授权卡片能力时，上述权限最小化原则可实现物理强制；无此能力的宿主以人类显式文字批准替代：

| 操作类型 | L1 行为 | L2 行为 | L3 行为 |
|---------|---------|---------|---------|
| 写入白名单内文件 | 自动允许 | 自动允许 | 授权卡片确认 |
| 写入白名单外文件 | Hook 阻断 → CCB | Hook 阻断 → CCB | Hook 阻断 → CCB |
| 执行构建/测试命令 | 自动允许 | 自动允许 | 自动允许 |
| 执行迁移/部署命令 | 禁止 | 授权卡片确认 | 禁止 |
| 合并到 `dev` | CI 通过后允许 | 禁止（人类操作） | 禁止（人类操作） |

### 2. 熔断与接管机制

| 触发条件 | 响应动作 |
|---------|---------|
| 同一阶段连续被自动化打回 ≥ 3 次 | 强制 `Blocked`，通知人类接管 |
| Token 消耗超过单任务预算 2 倍 | 暂停执行，等待人类评估 |
| 修改了可写白名单以外的文件 | Linter 拦截，进入 CCB 流程 |
| 任务 Cycle Time 超过预期 3 倍 | 自动发出预警，人类评估是否需要拆分或重新设计 |

#### 宿主熔断实现：Subagent 生命周期管理

宿主提供子代理管理能力时，熔断机制通过 subagent 生命周期管理实现：

- **强制终止**：当 subagent 触发熔断条件时，Main Agent 使用宿主终止 API 立即终止失控子代理
- **状态保存**：被终止的 subagent 的最后工作状态保留在任务文档中（仓库 `ACTIVE_TASK_T-XXX.md` 是唯一事实来源），支持人类介入后恢复
- **自动预警**：结合定时巡检，当检测到 subagent 运行时间或 Token 消耗异常时，主动向人类发出预警

### 3. Agent 可观测性

每个智能体任务完成后，应在 TASK 文档的效能数据中记录：
- **返工次数**：被打回重做的次数。
- **AI 代码生成占比**：Agent 生成 vs 人类修改的代码行比例。
- **Token 消耗**：本次任务的 API Token 总消耗。

这些数据在迭代回顾时进行聚合分析，用于调优 Agent 提示词和任务拆解粒度。

## 二十一、 新项目快速接入指南

SAGE 新项目推荐用 bootstrap 一键初始化：`uv run python skills/sage-workflow/core/scripts/bootstrap_sage.py --repo-root <项目绝对路径>`（先 `--dry-run` 预览）。以下为手动接入核对清单。

### 第一步：项目初始化

1. 创建 `AGENTS.md`：T1 导航入口，目标 ≤50 行，超过 80 行必须拆到 T2；包含项目概述、构建命令、关键行为规则和指向各层文档的路径。
2. 所有宿主共用单一 `AGENTS.md` 入口：工具差异由 `adapters/` 或项目本地覆盖承载，不创建工具覆盖入口副本（见 BP-006 修订口径）。
3. 填写**项目章程**（见第二章模板），获得 Sponsor 签字。
4. 填写**RACI 矩阵**和**沟通矩阵**（见第三章）。

### 第二步：工作流文件配置

5. bootstrap 或手动复制 `templates/`、`prompts/`、`docs/guides/`、`scripts/sage_linter.py` 与 Git hooks 到项目；宿主提供写入后钩子能力时，配置文件写入后自动触发 `sage_linter.py` 范围校验。
6. 创建 `docs/project/` 与 `scripts/`（bootstrap 自动完成）。
7. 定制 `docs/guides/development-standards.md` 中的构建、测试与部署命令。
8. 在 `docs/project/` 下创建 `PROJECT_BOARD.md`、`KNOWN_PATTERNS.md`、`DECISION_LOG.md`、`RISK_REGISTER.md`。

### 第三步：定时巡检配置（宿主支持时）

9. 配置定时巡检（cron 或宿主定时任务能力）：
   ```bash
   # WIP 状态巡检（每 30 分钟）
   "*/30 * * * *" "检查 PROJECT_BOARD.md WIP 状态，超限预警"
   # 文档新鲜度巡检（每日）
   "0 9 * * *" "运行 sage_linter.py 文档新鲜度扫描"
   ```

### 第四步：基线校验

10. 运行全量校验：
    ```bash
    uv run python scripts/sage_linter.py --all
    ```
    确保初始基线检查全部通过。

### 第五步：启动首个任务

11. 从 `templates/TASK-TEMPLATE.md` 物理复制出首个活跃任务文档（如 `docs/project/ACTIVE_TASK_T-001.md`）。
12. 在 `PROJECT_BOARD.md` 登记，指派给智能体开始执行。

### 第六步：建立节奏

13. 设定迭代周期（推荐 2 周）。
14. 安排首次迭代回顾会（见第十六章模板）。
15. 启动风险登记册定期评审。
